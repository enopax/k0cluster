**Last Updated**: 2025-12-04

## Admission Webhooks

### What Are Admission Webhooks?

Admission webhooks are Kubernetes extensions that intercept API requests **before** they are stored in etcd. They act as gatekeepers that can:

1. **Validate** requests (reject if invalid)
2. **Mutate** requests (modify before saving)

**Flow**:
```
kubectl apply -f resource.yaml
        ↓
   API Server
        ↓
Admission Controller
        ↓
Webhook HTTP Call → External Service (validates/mutates)
        ↓
   Approve/Reject
        ↓
 Save to etcd (if approved)
```

### k0rdent Webhooks

k0rdent installs several validating webhooks:

```bash
$ kubectl get validatingwebhookconfiguration | grep kcm
kcm-validating-webhook-configuration
```

**What it validates**:
- `ClusterDeployment` - Ensures templates and providers exist
- `Management` - Validates management cluster configuration
- `ProviderTemplate` - Checks provider specifications
- `ClusterTemplate` - Validates cluster definitions
- `Credential` - Verifies credential references

**Example: ClusterDeployment Validation**

When you run:
```bash
kubectl apply -f cluster-01.yaml
```

The webhook checks:
1. ✅ Does the `spec.template` reference exist?
2. ✅ Are all required providers deployed?
3. ✅ Does the `spec.credential` exist?
4. ✅ Is the configuration valid?

If any check fails, the webhook **rejects** the request immediately.

### Why Admission Webhooks Make Sense

**Benefits**:

1. **Fail Fast** - Catch errors immediately, not after 10 minutes of provisioning
2. **Prevent Invalid State** - Don't create resources that will fail
3. **Policy Enforcement** - Enforce organizational standards (quotas, naming, security)
4. **Data Integrity** - Ensure relationships exist (e.g., credentials for clusters)
5. **Security** - Prevent privilege escalation or unauthorized access

**Example Scenario**:

Without webhook:
```
User creates ClusterDeployment
→ k0rdent starts provisioning
→ 10 minutes later: "Error: infrastructure-hetzner provider not found"
→ User wastes time debugging
```

With webhook:
```
User creates ClusterDeployment
→ Webhook validates immediately
→ "Error: infrastructure-hetzner provider not deployed"
→ User fixes provider BEFORE wasting time
```

### Webhook Configuration Details

**Service**: The webhook runs as part of the kcm-controller-manager

```bash
$ kubectl get pods -n kcm-system | grep kcm-controller-manager
kcm-controller-manager-5975b88db7-hkskf   1/1     Running
```

**Certificate**: Auto-generated by cert-manager

```bash
$ kubectl get certificate -n kcm-system | grep webhook
kcm-serving-cert   True    kcm-webhook-server-cert
```

**Webhook Endpoints**:
- Service: `kcm-webhook-service.kcm-system.svc`
- Port: 9443
- Path: Various (e.g., `/validate-k0rdent-mirantis-com-v1beta1-clusterdeployment`)

### Should Webhooks Be Disabled?

**Generally: NO**

Disabling webhooks removes critical validation and can lead to:
- Invalid resource creation
- Failed deployments with cryptic errors
- Security vulnerabilities
- Data inconsistency

**Exception**: During development/debugging, you might temporarily bypass webhooks to test edge cases.

## Telemetry

### Overview

k0rdent includes a telemetry component that reports usage data to Mirantis.

```bash
$ kubectl get pods -n kcm-system | grep telemetry
kcm-regional-telemetry-8465bf9f99-czcjg   1/1     Running
```

### Configuration

**Current Settings**:
```yaml
args:
  - --telemetry-mode=online        # Sends data to Mirantis
  - --telemetry-interval=1h        # Reports every hour
  - --telemetry-concurrency=5      # Max 5 concurrent requests
  - --telemetry-jitter=10          # Random 10% delay to spread load
```

### What Data Is Sent?

Based on typical telemetry implementations:

**Likely Included**:
- Installation ID (anonymized UUID)
- k0rdent version
- Kubernetes version
- Number of clusters managed
- Provider usage (e.g., "3 AWS, 1 Azure")
- Cluster states (ready, failed, etc.)
- Error events (types, not details)
- Resource counts
- Feature usage flags

**NOT Included**:
- Credentials or secrets
- Workload data or pod names
- Infrastructure details (IPs, hostnames)
- Personal information
- Application logs

### Is This Sent to Mirantis?

**YES** - in `online` mode, telemetry is sent to Mirantis servers.

**Endpoint**: Likely `https://telemetry.mirantis.com` or similar (check network traffic to confirm)

**Purpose**:
- Product improvement
- Bug detection
- Usage analytics
- Feature prioritization

### Privacy & Compliance Concerns

**Considerations**:

1. **Data Sovereignty** - Data leaves your infrastructure to external servers
2. **GDPR Compliance** - May require disclosure in privacy policies
3. **HIPAA/PCI** - May violate compliance requirements for sensitive environments
4. **Corporate Policy** - Some organizations prohibit external telemetry
5. **Air-Gapped Environments** - Cannot work without internet access

### Should Telemetry Be Disabled?

**Disable if**:
- ✅ Operating in regulated environment (GDPR, HIPAA, PCI-DSS)
- ✅ Corporate policy prohibits external data transmission
- ✅ Air-gapped or restricted network
- ✅ Privacy-first requirements
- ✅ No active Mirantis support contract

**Keep enabled if**:
- ✅ Using Mirantis support (telemetry may be required)
- ✅ Want to contribute to product improvement
- ✅ No compliance restrictions
- ✅ Trust Mirantis data handling

**Recommendation**: For production environments, **disable telemetry** unless explicitly required by support contract.

## How to Disable Telemetry

### Option 1: Helm Values (Recommended)

If reinstalling or upgrading k0rdent:

```bash
helm upgrade kcm oci://ghcr.io/k0rdent/kcm/charts/kcm \
  --version 1.5.0 \
  -n kcm-system \
  --reuse-values \
  --set regional.enabled=false
```

### Option 2: Scale Down Deployment

Temporary disable (survives pod restarts, not upgrades):

```bash
kubectl scale deployment kcm-regional-telemetry \
  -n kcm-system \
  --replicas=0
```

Verify:
```bash
$ kubectl get pods -n kcm-system | grep telemetry
# Should show no pods
```

### Option 3: Delete Deployment

Permanent removal (may be recreated on Helm upgrade):

```bash
kubectl delete deployment kcm-regional-telemetry -n kcm-system
```

### Option 4: Network Policy (Advanced)

Block egress traffic from telemetry pod:

```yaml
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: block-telemetry
  namespace: kcm-system
spec:
  podSelector:
    matchLabels:
      app.kubernetes.io/name: kcm-regional-telemetry
  policyTypes:
  - Egress
  egress:
  - to:
    - namespaceSelector:
        matchLabels:
          name: kube-system
    ports:
    - protocol: TCP
      port: 53  # Allow DNS only
```

This allows DNS but blocks external HTTP/HTTPS.

### Option 5: Offline Mode

Change to offline mode (stores locally, doesn't send):

```bash
kubectl edit deployment kcm-regional-telemetry -n kcm-system
```

Change:
```yaml
args:
  - --telemetry-mode=offline  # Was: online
```

## Verification

### Check Telemetry Status

```bash
# Is it running?
kubectl get pods -n kcm-system | grep telemetry

# Check configuration
kubectl get deployment kcm-regional-telemetry -n kcm-system -o yaml | grep telemetry-mode

# Check logs (if running)
kubectl logs -n kcm-system -l app.kubernetes.io/name=kcm-regional-telemetry
```

### Check Webhook Status

```bash
# List webhooks
kubectl get validatingwebhookconfiguration
kubectl get mutatingwebhookconfiguration

# Describe k0rdent webhook
kubectl describe validatingwebhookconfiguration kcm-validating-webhook-configuration

# Test webhook (should reject invalid resource)
cat <<EOF | kubectl apply -f -
apiVersion: k0rdent.mirantis.com/v1beta1
kind: ClusterDeployment
metadata:
  name: test
  namespace: kcm-system
spec:
  template: non-existent-template
  credential: fake-credential
EOF
# Expected: Error from admission webhook
```

### Monitor Network Traffic

To confirm telemetry destination:

```bash
# On the telemetry pod
kubectl exec -n kcm-system deployment/kcm-regional-telemetry -- netstat -an | grep ESTABLISHED

# Or check pod logs for HTTP requests
kubectl logs -n kcm-system -l app.kubernetes.io/name=kcm-regional-telemetry --tail=100 | grep -i "http\|post\|send"
```

## Security Best Practices

### Webhooks

1. **Keep Enabled** - Don't disable unless absolutely necessary
2. **Monitor Logs** - Watch webhook-related errors for configuration issues
3. **Certificate Rotation** - Ensure cert-manager is working (auto-renewal)
4. **Backup Certificates** - In case of cert-manager failure

### Telemetry

1. **Review Privacy Policy** - Understand what Mirantis collects
2. **Compliance Check** - Ensure telemetry meets your requirements
3. **Document Decision** - Record why telemetry is enabled/disabled
4. **Network Segmentation** - Use NetworkPolicies if keeping enabled
5. **Audit Logs** - Monitor what data is sent (if possible)

## Troubleshooting

### Webhook Issues

**Problem**: ClusterDeployment rejected by webhook

**Solution**:
1. Check webhook logs:
   ```bash
   kubectl logs -n kcm-system -l control-plane=kcm-controller-manager | grep webhook
   ```
2. Verify webhook service is running:
   ```bash
   kubectl get svc kcm-webhook-service -n kcm-system
   ```
3. Check certificate validity:
   ```bash
   kubectl get certificate kcm-serving-cert -n kcm-system
   ```

**Problem**: Webhook times out

**Solution**:
1. Check controller health:
   ```bash
   kubectl get pods -n kcm-system | grep kcm-controller-manager
   ```
2. Increase timeout (last resort):
   ```bash
   kubectl edit validatingwebhookconfiguration kcm-validating-webhook-configuration
   # Change: timeoutSeconds: 30
   ```

### Telemetry Issues

**Problem**: Telemetry pod CrashLoopBackOff

**Solution**:
1. Check logs:
   ```bash
   kubectl logs -n kcm-system -l app.kubernetes.io/name=kcm-regional-telemetry
   ```
2. Common causes:
   - Network connectivity issues (in air-gapped environments)
   - Invalid configuration
   - Resource constraints

**Solution**: If not needed, just scale to 0 replicas.

## Decision Matrix

### Should I Disable Telemetry?

| Environment | Recommendation | Reason |
|-------------|----------------|---------|
| Production | **Disable** | Privacy, compliance, security |
| Staging | **Disable** | May contain sensitive data |
| Development | Keep enabled | Helps product improvement |
| Air-gapped | **Disable** (will fail anyway) | No internet access |
| Mirantis Support | Keep enabled | May be required for support |
| GDPR/HIPAA | **Disable** | Compliance requirement |
| Personal/Learning | Your choice | No compliance concerns |

### Should I Disable Webhooks?

| Scenario | Recommendation | Reason |
|----------|----------------|---------|
| Production | **Keep enabled** | Critical validation |
| Staging | **Keep enabled** | Catch errors early |
| Development | **Keep enabled** | Learn proper workflows |
| Debugging specific issue | Temporary disable | Isolate problem |
| Testing edge cases | Temporary disable | Test invalid states |

**Bottom Line**: Always keep webhooks enabled unless debugging. Consider disabling telemetry based on your compliance and privacy requirements.
